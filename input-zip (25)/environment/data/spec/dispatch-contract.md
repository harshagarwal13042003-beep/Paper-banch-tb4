# Cold-chain dispatch reconciliation contract

This is the normative, offline contract for the supplied multi-depot operation. The initial `/app/state/dispatch.sqlite` database is **corrupted operational state**, not an answer. The frozen source feeds are read-only. Only the final database and both published JSON files are graded. A correct solution may use any method or tools; CLI operations are offered as a working control surface, not as required steps.

## Sources and clock

The input root is `/app/input/`, with `/app/input/manifest.json`, `/app/input/depots.json`, `/app/input/lanes.json`, `/app/input/dock_slots.json`, `/app/input/orders.json`, `/app/input/lots.json`, `/app/input/vehicles.json`, `/app/input/drivers.json`, `/app/input/incidents.json`, `/app/input/thermal.json`, `/app/input/receipts.json`, and `/app/input/handoffs.json`. The manifest SHA-256 digests cover all other `.json` feed bytes. All timestamps are integer minutes from a shared operational epoch; wave 0 denotes pre-cutover, already dispatched orders, and waves 1–5 are the interrupted recovery waves. Times use the same epoch across feeds and outputs. Identifiers are case-sensitive.

The 4 depots have dedicated stock, docks, drivers and vehicles. In a lane record, `minutes` is one-way travel time from `depot` to `destination`. The `dock_slots` feed lists the allowed `(depot,wave,dock,depart)` appointments. One outbound run may use each slot, at most one run per vehicle and one run per driver in the same wave. A *run* is exactly one `(depot,wave,destination)` group. Every active order in that group must be loaded on the same run; it may draw from several inventory lots. There are 60 required runs, one for each group with active demand. Each run must have a unique nonempty `trip_key`; no specific spelling is required.

## Demand, existing history and exceptions

Every `orders.json` row with `status="open"` must be fulfilled **in full**: the sum of planned `allocations.qty` for its `id` equals its `qty`. No discretionary shortage exceptions are allowed. The feasible instance was constructed to make full fulfillment possible. Orders with `status="cancelled"` must have no planned allocations, and must have exactly one `exceptions` row whose `incident_id` is the cancellation incident for that order and whose `reason` is `cancelled-by-customer`. No other exception rows are allowed. These requirements prevent falsely passing by cancelling work.

The rows in `/app/input/handoffs.json` are completed wave-0 handoffs. Their corresponding `allocations` database records, including every original column, must remain byte-for-value unchanged and marked `completed`. They consume inventory but are excluded from new fleet/driver scheduling. New rows have `status="planned"`. Planned order IDs must exist in the frozen orders feed; no phantom dispatches.

The initial `reservations` table contains invalidated, pre-cutover provisional reservations. Every original reservation must be retained with identical `id`, `order_id`, `lot_id`, `qty` and `vehicle` and final `state="released"`. Each requires exactly one `release_log` entry with `reservation_id` equal to that reservation ID, `incident_id="CUTOVER-001"` and `reason="invalidated-by-cutover"`. There may be no extra release records. The active recovery allocation set is independent of these stale reservations; their units must not be deducted again. The initial database's `meta` table must remain exactly `{"source_id":"CUTOVER-2026-11"}`.

## Inventory, FEFO, receipts and temperature

Stock is counted in whole units. A planned order may be split across lots, never across runs. All lots must match the order depot and SKU. Global allocation precedence is the ascending pair `(order.wave, order.id)`; within each order, eligible lots **must** be consumed in ascending `(expires_at,lot.id)` order before using a later-expiring lot. For each order take from the first eligible lot up to its unconsumed capacity, then the next; no skipping is allowed. Completed handoff units are deducted from their lots before all recovery-wave allocations. No lot may ship more than its frozen `qty`.

A lot is eligible for a run only when `lot.available_at <= run.depart` and `run.depart + lane.minutes < lot.expires_at`. Quarantine incidents with `kind="quarantine"` block the specified `lot_id` from `effective_wave` onward. Cumulative ambient exposure for a lot at wave W equals `initial_exposure + sum(exposure_added for ambient incidents at lot.depot with wave <= W)`. It must not exceed `max_exposure`. These checks apply to planned shipment only. Each inter-depot receipt must satisfy `received_at = released_at + travel_minutes + delay_minutes`, and the receiving lot's `available_at` must equal `received_at`; the destination depot must match the lot depot. Even if a receipt is delayed, reserved units cannot ship until physically available. A run reaches the customer at `depart + lane.minutes`, inclusive of the order's `appointment_start` and `appointment_end`.

## Fleet, docks, drivers and cumulative effects

Every run uses an existing vehicle and driver whose home `depot` matches the run depot, plus an allowed dock slot. Vehicle capacity must be at least the **sum of quantities of distinct orders** on the run, not the number of allocation rows (which can be larger when lots are split). The vehicle and driver are both on duty from departure until the trip return-and-unload time, `depart + 2 * lane.minutes + 15`. The whole interval must lie within their `shift_start` and `shift_end`. Each wave may use a particular driver or vehicle on at most one run.

For driver D, cumulative duty minutes across all recovery waves equal the sum of `2 * lane.minutes + 15` for assigned runs, and must not exceed `max_duty`. When consecutive runs assigned to the same driver are ordered by departure time, the next departure must be at least the preceding return-and-unload time plus `min_rest`. Vehicles have the analogous minimum inter-run turnaround (`min_turnaround`). The `thermal.json` feed supplies `warm_minutes` for each `(vehicle,wave)` pair. A vehicle cannot operate a run if `warm_minutes > reefer_max_exposure`, or if total `warm_minutes` for all assigned recovery-wave runs exceeds `cumulative_warm_budget`. `breakdown` and `stranded` incidents forbid the named vehicle from `effective_wave` through `through_wave`, inclusive. These constraints couple earlier assignments to later waves.

## Database and outputs

The existing SQLite schema is authoritative. Final tables are `allocations(order_id,lot_id,qty,wave,vehicle,driver,dock,depart,trip_key,status)`, `reservations(id,order_id,lot_id,qty,vehicle,state)`, `release_log(reservation_id,incident_id,reason)`, `exceptions(order_id,incident_id,reason)`, and `meta(key,value)`. Keep the original schema, table names and primary keys. Do not install triggers that alter behavior. The SQLite database must pass `PRAGMA quick_check`. The three final deliverables are `/app/state/dispatch.sqlite`, `/app/output/dispatch-manifest.json`, and `/app/output/exception-ledger.json`. After completion, publishing the same reconciled state again must be byte-identical and must not mutate the database.

Both JSON files are UTF-8 canonical JSON: `json.dumps(value,sort_keys=True,separators=(',',':')) + '\n'`, no indentation. The manifest is an object with exactly `version=1`, `source_id="CUTOVER-2026-11"`, `allocations`, `runs`, and `planned_units`. `allocations` is a list of all database allocation rows as objects with the ten listed columns, ordered `(wave,order_id,lot_id)`. `planned_units` is the sum of `qty` for `status="planned"`. `runs` contains one object for every planned trip, with exactly `trip_key,wave,vehicle,driver,dock,depart,orders`. `orders` is the lexically sorted unique list of IDs on the trip; trips are sorted by `(wave,trip_key)`. The exception ledger is an object with exactly `version=1`, `exceptions`, and `releases`. Its arrays mirror the database tables, ordered by `order_id` and `reservation_id`, respectively. No other records are permitted. Multiple valid fleet assignments are accepted if they satisfy every constraint.

## Management commands

`/app/bin/dispatchctl` is available and works correctly; it has no automatic reconciliation command. The CLI supports `status`, `inspect ORDER_ID`, `slots DEPOT WAVE`, `release RESERVATION_ID INCIDENT_ID [--reason VALUE]`, `allocate ORDER_ID LOT_ID VEHICLE DRIVER DOCK TRIP_KEY QTY DEPART`, `exception ORDER_ID INCIDENT_ID [--reason VALUE]`, `reset-planned [--wave N]`, `validate`, and `publish`. Optional `--db`, `--input`, and `--output` flags precede the subcommand and accept absolute paths. `validate` is a quick operational diagnostic, **not** the complete contract verifier. The JSON source feeds and authoritative contract remain available for other methods, including local SQL or scripts. The result is graded on the final state, not the command sequence.
